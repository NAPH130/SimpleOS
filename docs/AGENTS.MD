# SimpleOS 开发约定

这些约定适用于 SimpleOS 的代码开发、评审和文档维护。

## 依据现有文档开发

- 修改前阅读 [文档索引](README.md)、[内核架构概览](architecture/overview.md) 和 [开发路线](plan/roadmap.md)。涉及具体模块时，再查看对应的实现说明、待办、源码和测试。
- 以源码、构建规则和可复现的测试结果核对当前行为。需求或设计文档与实现有出入时，先弄清差异，再同步修正文档。`TEMP/` 用于存放参考资料和临时草案。
- 沿用当前模块边界和已确认的阶段目标。先做当前目标所需的改动，后续工作记入对应计划。

## 架构与可维护性

- 按职责放置代码。x86_64 专属的寄存器、描述符表和汇编入口放在 `src/arch/x86_64/`，设备操作放在 `src/drivers/`，内核服务和各子系统的处理策略放在对应模块。跨模块接口在 `include/` 中声明。
- 优先复用现有接口和数据结构。新增接口时，明确调用方、参数、返回值和失败行为。修改共享接口时核对调用方、构建入口和测试。
- 使用清楚的名称和小而完整的函数。将硬件常量、向量号和布局约定集中维护，尤其是汇编和 C++ 共用的结构。必要时用 `static_assert` 检查尺寸和偏移。
- 内核代码遵循 freestanding C++17 的构建约束。涉及 CPU 指令或调用约定的细节在架构层处理，把可用 C++ 表达的分发和策略留在相应模块。

## 说明性注释

- 用简洁的中文说明代码的作用、这样写的原因，以及调用方必须满足的条件。沿用项目里的术语，按代码实际行为维护注释。
- 优先解释从代码难以直接看出的信息，例如硬件要求的字段布局、单位、寄存器保存顺序、中断状态，以及返回或停机的条件。
- 让命名和结构说明直观的操作。注释放在相关代码旁，每段解释一个目的。`TODO` 写明待完成的行为，跨阶段任务可链接到 `docs/plan/` 下的对应计划。

## 验证与更新文档

- 根据变更范围执行相关构建和测试。内核启动、异常入口或底层接口发生变化时，用 QEMU 核对可观察的结果。记录实际运行的命令和结果。 [构建、运行与验证](guides/getting-started.md)
- 功能、接口或使用方式有变化时，同步更新 `docs/architecture/` 的实现说明、`docs/guides/` 的使用或验证方法，以及 `docs/plan/` 的进度和验收结果。
- 新增正式文档时更新 [文档索引](README.md)，使用相对链接指向相关源码和文档。项目概况、快速启动或文档入口发生变化时，同步维护 [根目录 README](../README.md)。
